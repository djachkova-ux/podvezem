# Трекер разработки «Подвезём»

Один пункт плана = одна сессия Claude Code. Задача трекера — чтобы **сессия не превышала ~200 000 токенов** и следующая начиналась без пересказа предыдущей.

Как стартовать сессию: открыть новый чат в папке проекта и написать
`Читай ТРЕКЕР-РАЗРАБОТКИ.md, делаем сессию S2` — этого достаточно.

---

## Правила экономии контекста (главное)

1. **Читать только то, что перечислено в блоке «Читать» текущей сессии.** Остальные файлы — через `Grep`/`Glob`, а не целиком.
2. **Никогда не читать целиком `design/board-drivers.html`** (~1400 строк, это ≈40 000 токенов). Это визуальный референс: смотреть его в браузере, а цвета и шрифты брать из `design/tokens.css` (~150 строк).
3. **ТЗ читать по разделам**, а не целиком: нужный раздел ищется `Grep` по заголовку (`## 6`, `## 7` и т. д.).
4. **Один файл — одна задача, ≤ 250 строк.** Экран больше 250 строк — выносить куски в `src/components/`. Большие файлы дорого перечитывать в следующих сессиях.
5. **Не открывать** `node_modules/`, `dist/`, `package-lock.json`, содержимое `.firebase/`.
6. **Не вставлять в чат длинные выводы**: сборку и тесты запускать так, чтобы в ответ шли только ошибки (`npm run build 2>&1 | Select-Object -Last 20`).
7. **Не переписывать файл целиком ради правки в двух строках** — точечные `Edit`.
8. **Правило 60 %:** как только израсходовано около 60 % контекста, а сессия не закончена — не начинать новую подзадачу. Довести текущую до рабочего состояния, обновить трекер, сделать коммит и хэндофф.
9. **Финиш каждой сессии:** отметить статус в таблице ниже → коммит → обновить `ХЭНДОФФ-Школьный-трансфер.md` (перезаписывать, не накапливать).

## S6 · Отклики заказчика → подтверждение водителем

- **Цель:** ключевая логика приложения, самая аккуратная сессия.
- **Читать:** ТЗ раздел 7, `src/lib/db.js`.
- **Файлы:** `src/screens/RespondSheet.jsx`, `src/screens/OfferResponses.jsx`, транзакции в `db.js`.
- **Готово когда:** отклик с выбором детей не превышает свободные места; подтверждение уменьшает места **транзакцией**; при нуле предложение закрывается и уходит с доски.
- **Осторожно:** два одновременных подтверждения не должны увести места в минус — только `runTransaction`.
- **Сделано:** `src/lib/db.js` — `subscribeRideOffer(offerId, callback)` (подписка на одно предложение, нужна экранам отклика/списка откликов), `createResponse(uid, profile, offer, { childrenIds, note })` (коллекция `responses`, снимок данных заказчика + выбранных детей + `offerDriverId` — денормализованный владелец предложения для правил и запроса списка), `subscribeOfferResponses(offerId, callback)` (запрос по `offerId`, сортировка по `createdAt` на клиенте), `confirmResponse(response)` (`runTransaction`: проверяет `status === 'pending'` и `seatsFree >= children.length`, уменьшает `seatsFree`, при 0 переводит предложение в `status: 'closed'`, отклик — в `confirmed`), `rejectResponse(responseId)` (обычный `updateDoc`, без транзакции). `firestore.rules` — новый блок `responses`: читают только участники (`customerId` или `offerDriverId`), создаёт заказчик, подтверждает/отклоняет только водитель-владелец предложения. **Не опубликован в консоли** — см. хэндофф. `src/screens/RespondSheet.jsx` (новый, `/board/drivers/:offerId/respond`) — заказчик выбирает детей (чекбоксы ограничены `offer.seatsFree`, при достижении лимита остальные чекбоксы дизейблятся), комментарий, гейт по `isCustomer && address && children.length > 0` (как в `NewRequest.jsx`), отдельное состояние для «поездка больше не открыта». `src/screens/OfferResponses.jsx` (новый, `/board/drivers/:offerId/responses`) — водитель видит список откликов на своё предложение (карточка на классах `board.css`, как и `RequestCard`), кнопки «Подтвердить»/«Отклонить» для `pending`, статус-текст для решённых; гейт по `offer.driverId === user.uid`; ошибки транзакции (`not-enough-seats` при гонке двух подтверждений) показываются отдельным сообщением, не роняют экран. `src/components/RideCard.jsx` — кнопка «Откликнуться» теперь активная ссылка на `RespondSheet` (не своя поездка) или на `OfferResponses` («Отклики», своя поездка). Два новых маршрута в `App.jsx`. Проверено в браузере тестовым аккаунтом `+7 900 222-33-01`: форма отклика открывается по ссылке с доски, лимит по местам работает (офер с 1 местом → максимум 1 ребёнок), гейт и переход на «Отклики» для своего предложения — рендерятся корректно. После публикации правил в консоли пройден сценарий целиком на двух аккаунтах: отклик → подтверждение (места уменьшились, предложение ушло с доски) и отклик → отклонение (места не тронуты). По пути найден и исправлен баг: `subscribeOfferResponses` фильтровала список только по `offerId`, а правило чтения проверяет `resource.data.offerDriverId` — Firestore не вычисляет правила построчно для list-запросов, а требует, чтобы сам запрос статически гарантировал соответствие правилу, поэтому весь список отклонялся `permission-denied`, хотя `create` при этом проходил нормально (это одиночная запись, не list). Фикс — добавить `where('offerDriverId', '==', driverUid)` вторым условием запроса; `subscribeOfferResponses` теперь принимает `(offerId, driverUid, callback)`.

## S7 · Отклики водителя → подтверждение заказчиком

- **Цель:** зеркальный сценарий.
- **Читать:** ТЗ раздел 8, `src/screens/OfferResponses.jsx` (как образец).
- **Готово когда:** подтверждённый отклик закрывает запрос и создаёт активную поездку у обеих сторон.
- **Сделано:** решение по схеме (было открытым вопросом в хэндоффе S6) — отдельная коллекция `requestResponses`, а не переиспользование `responses` с полем-различителем: у запроса нет счётчика мест, поля и правила симметричны, но по смыслу разные, отдельная коллекция чище. `src/lib/db.js` — `subscribeRequest(requestId, callback)` (подписка на один запрос), `createRequestResponse(uid, profile, request, { note })` (без выбора детей — водитель откликается на весь запрос целиком, не на часть), `subscribeRequestResponses(requestId, customerUid, callback)` (фильтр по `requestId` **и** `requestCustomerId` — тот же приём из «Важного технического урока» S6, с самого начала), `confirmRequestResponse(response)` (`runTransaction`: у запроса нет `seatsFree`, подтверждение любого одного отклика сразу переводит запрос в `status: 'closed'`; транзакция нужна, чтобы два одновременных подтверждения разных откликов не закрыли запрос дважды — проверяет `request.status === 'open'` и `response.status === 'pending'`), `rejectRequestResponse(responseId)` (обычный `updateDoc`). `firestore.rules` — новый блок `requestResponses`, симметричный `responses` (`read` — участники по `driverId`/`requestCustomerId`, `create` — водитель, `update` — заказчик-владелец запроса). **Не опубликован в консоли** — см. хэндофф. `src/screens/RequestRespondSheet.jsx` (новый, `/board/requests/:requestId/respond`) — водитель отправляет отклик с необязательным комментарием (без выбора детей, в отличие от `RespondSheet.jsx`), гейт по `isDriver && car.plate && pickupQueues.length > 0` (как в `NewOffer.jsx`), отдельное состояние «запрос больше не открыт». `src/screens/RequestResponses.jsx` (новый, `/board/requests/:requestId/responses`) — заказчик видит отклики водителей (имя, авто, очереди, телефон с `tel:`), кнопки «Подтвердить»/«Отклонить» для `pending`; кнопка подтверждения дополнительно дизейблится, если запрос уже закрыт (`request.status !== 'open'`) — подстраховка от гонки на UI, транзакция всё равно единственный источник истины. `src/components/RequestCard.jsx` — кнопка «Откликнуться» стала активной ссылкой на `RequestRespondSheet` (чужой запрос) или на `RequestResponses` («Отклики», свой запрос) — убран старый `disabled`-заглушка. Два новых маршрута в `App.jsx`. После публикации правил в консоли пройден сценарий целиком на трёх аккаунтах: **подтверждение** — заказчик `...-01` (Ирина Ковалёва) создал запрос, водитель `...-02` (Дмитрий Панов) откликнулся с комментарием, заказчик подтвердил → запрос получил `status: 'closed'`, отклик — `confirmed`, запрос пропал с доски «Запросы» (было 1, стало 0); **отклонение** — второй запрос, отклик водителя `...-03` (Марина Швец), заказчик отклонил → отклик получил `status: 'rejected'`, запрос остался `status: 'open'` и виден на доске. Гонка двух подтверждений разных откликов на один запрос не воспроизводилась намеренно (как и `not-enough-seats` в S6), но механизм в `confirmRequestResponse` заложен и проверен по коду.
