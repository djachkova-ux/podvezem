Дата: 03.09.2026. Сессия: **S9 — повторяющиеся предложения**. ✅ Проверено в браузере: генерация по шаблону на выбранные дни недели, негативный случай (невыбранный день пуст).

## Что сделано в S9

Опция «Повторять» в создании предложения (ТЗ 6.1) — водитель задаёт шаблон «дни недели + время + места» вместо одной даты, предложения на месяц вперёд создаются сразу все, одним действием.

- **Схема (был открытый вопрос в хэндоффе S8):** оба варианта из вопроса сразу, не один вместо другого. Отдельная коллекция `offerTemplates` хранит параметры шаблона (`driverId`, `weekdays`, `arrivalTime`, `seatsTotal`, `note`, `createdAt`) — для истории и возможного будущего экрана управления. Каждый сгенерированный документ `rideOffers` при этом получает поле-маркер `templateId`, но **не зависит** от шаблона и от других сгенерированных предложений — это самостоятельные документы. Отмена/удаление одного (уже разрешено правилом `delete` водителю-владельцу ещё с S3) никак не задевает остальные даты шаблона.
- **`src/lib/dates.js`** — `WEEKDAY_OPTIONS` (Пн первым, как в ру-интерфейсах; значения — домен `Date#getDay()`, 0=вс), `REPEAT_HORIZON_DAYS = 30`, `getRepeatDates(weekdays, horizonDays, from)` — список дат (YYYY-MM-DD) на горизонт вперёд, чей день недели входит в `weekdays`. Горизонт начинается **с завтра, не с сегодня** — иначе для сегодняшнего дня недели публикация вечером создавала бы предложение на уже прошедшее сегодня время прибытия.
- **`src/lib/db.js`** — `createRideOfferTemplate(uid, profile, { weekdays, arrivalTime, seatsTotal, note })`: один `writeBatch` — документ шаблона плюс по одному `rideOffers` на каждую подходящую дату (данные водителя/авто/очередей — тот же снимок из профиля, что в обычном `createRideOffer`). Не `runTransaction` — это независимые создания новых документов, не конкурентная правка существующих счётчиков, гонки здесь нет.
- **`src/screens/NewOffer.jsx`** — чекбокс «Повторять по дням недели (на месяц вперёд)» переключает поле «Дата» на мультивыбор дней недели пилюлями. Переиспользованы существующие классы `checkbox-row`/`checkbox-group`/`checkbox-chip` из `forms.css` (уже применялись для похожих мультивыборов в `NewRequest.jsx`/`Profile.jsx`/`Register.jsx`) — новых стилей не потребовалось. Клиентская валидация: «Выберите хотя бы один день недели», если «Повторять» включён, а дней не выбрано.
- **`firestore.rules`** — новый блок `offerTemplates`: `read`/`create` только владельцу-водителю (`request.auth.uid == driverId`). `update`/`delete` не добавлялись — управление уже созданным шаблоном (переименовать, остановить повтор) не входит в UI этой сессии, шаблон нужен пока только на запись и как задел на будущее. Правило `rideOffers` менять не пришлось: `create` уже проверяет `driverId` владельца, а `templateId` — просто ещё одно поле того же документа, под существующее правило подпадает без изменений.
  - **Правила публиковал пользователь вручную** (по запросу пользователя — не через браузер), проверено после публикации.

## Принятые решения (накопительно)

- **Открытый вопрос S8 закрыт:** шаблон повтора — не «или/или» между отдельной коллекцией и полем-маркером, а оба сразу: коллекция `offerTemplates` для параметров + `templateId` на каждом сгенерированном `rideOffers` для прослеживаемости, без взаимной зависимости между документами.
- **Горизонт генерации фиксированный — 30 дней, не настраивается пользователем.** ТЗ 6.1 говорит «например, месяц» как пример, не как обязательно гибкий параметр; фиксированное значение проще и достаточно для v1.
- **Генерация — сразу вся, при создании шаблона, без фонового джоба.** Firebase-проект на Spark (без Cloud Functions/Cloud Scheduler на регулярной основе), поэтому продлевать горизонт «catящейся» генерацией на бэкенде не на чем; если шаблон понадобится продлить дальше 30 дней — это создание нового шаблона той же формой, отдельного UI под «продлить» в этой сессии нет.
- **Отмена одной даты шаблона — уже работает без нового кода**, т.к. каждый `rideOffers` независим и правило `delete` у водителя-владельца существует с S3; специальный UI под «удалить один день» в этой сессии не строился (ТЗ его не требует), но ничего не мешает добавить кнопку в будущем экране «Мои предложения», если понадобится.
