Дата: 03.09.2026. Сессия: **S6 — отклики заказчика → подтверждение водителем**. ✅ Проверено в браузере целиком, включая транзакцию.

## Что сделано в S6

Ключевая логика: заказчик откликается на предложение водителя, водитель подтверждает или отклоняет, свободные места уменьшаются транзакцией.

- **`src/lib/db.js`** — `subscribeRideOffer(offerId, callback)` (подписка на один документ `rideOffers`); `createResponse(uid, profile, offer, { childrenIds, note })` — публикует документ в новую коллекцию `responses`: снимок данных заказчика, выбранное подмножество `profile.children`, плюс `offerId` и **`offerDriverId`** (денормализованный владелец предложения); `subscribeOfferResponses(offerId, driverUid, callback)` — запрос по `offerId` **и** `offerDriverId`, сортировка по `createdAt` на клиенте; `confirmResponse(response)` — **`runTransaction`**: заново читает `offer` и `response`, проверяет `status === 'pending'` и `seatsFree >= children.length`, уменьшает `seatsFree`, при нуле закрывает предложение (`status: 'closed'`) и подтверждает отклик; `rejectResponse(responseId)` — обычный `updateDoc`, без транзакции.
- **`firestore.rules`** — блок `responses`: `read` — только участники (`customerId` или `offerDriverId`), `create` — заказчик, `update` — водитель-владелец предложения. `delete` не разрешён никому (отмена — часть S8). **Опубликован пользователем в консоли, проверено.**
- **`src/screens/RespondSheet.jsx`** (новый, `/board/drivers/:offerId/respond`) — заказчик выбирает детей (чекбоксы ограничены `offer.seatsFree`, лишние дизейблятся), комментарий, гейт по `isCustomer && address && children.length > 0`.
- **`src/screens/OfferResponses.jsx`** (новый, `/board/drivers/:offerId/responses`) — водитель видит список откликов (карточка `ResponseCard` объявлена внутри файла, переиспользует классы `board.css`), кнопки «Подтвердить»/«Отклонить» для `pending`, статус-текст для решённых, ошибки транзакции — баннером над списком.
- **`src/components/RideCard.jsx`** — кнопка «Откликнуться» из `disabled`-заглушки стала `Link` на `RespondSheet` (чужое предложение) или `OfferResponses` (своё, подпись «Отклики»).
- Два новых маршрута в `App.jsx`. `RequestsBoard`/`RequestCard` (S5) не трогали — зеркальный сценарий (отклик водителя на запрос) это S7.

## Важный технический урок сессии (пригодится в S7)

`subscribeOfferResponses` изначально фильтровала список только по `offerId`, хотя правило чтения проверяет `resource.data.offerDriverId`. Результат — `permission-denied` на **весь** список, хотя `create` (одиночная запись) при этом проходил нормально. Причина: **Firestore не вычисляет security rules построчно для `list`/collection-запросов** — он статически проверяет, может ли сам запрос в принципе вернуть документ, не проходящий правило; если гарантии нет, отклоняется весь запрос целиком, а не отдельные документы. Фикс — добавить в сам запрос `where()` по тому полю, которое проверяет правило (`offerDriverId`), чтобы Firestore мог доказать безопасность запроса без построчной проверки. Множественные `where()` только с равенством (без `orderBy` на другом поле) не требуют композитного индекса — сработало сразу, без ручного создания индекса в консоли.

**Для S7:** если схема получит поля вроде `requestCustomerId` (симметрично `offerDriverId`), любой list-запрос стороны, читающей чужие отклики, должен фильтровать именно по тому полю, что стоит в правиле `read`, а не только по `requestId`/`offerId`. Держать это в голове с самого начала, а не находить повторно.

## Принятые решения (накопительно)

- Схема `responses`: `offerId`, `offerDriverId` (денормализация ради правил и list-запроса без composite-индекса), `customerId`, `customerName`, `customerPhone`, `address`, `homeQueue`, `children[]` (снимок `{id, name, age}`), `date`, `arrivalTime`, `note?`, `status: 'pending' | 'confirmed' | 'rejected'`, `createdAt`.
- Уменьшение `seatsFree` и смена `status` — только внутри одной `runTransaction`, которая заново читает оба документа. Два параллельных подтверждения, суммарно превышающих места, не уводят счётчик в минус: вторая транзакция увидит уже уменьшённый `seatsFree` и бросит `not-enough-seats` (в этой сессии гонка не воспроизводилась намеренно, но механизм заложен и проверен по коду).
- **List-запросы и security rules: фильтровать по тому полю, что проверяет правило `read`**, а не только по логически нужному (см. «Важный технический урок» выше) — общее правило для всех будущих list-подписок в проекте, не только S7.
- `delete` для `responses` не разрешён — отмена своего отклика и снятие подтверждённого резерва (п.7.7 ТЗ) — это S8.
- «Активная поездка» (п.7.6 ТЗ) отдельной сущностью не заводилась — подтверждённый отклик (`status: 'confirmed'` в `responses`) уже содержит нужные данные; экран «Мои поездки» (S8) будет читать эту же коллекцию.
- Ошибки транзакции (`not-enough-seats`, `already-handled`) — обычные `Error` с машинно-читаемым `message`, ловятся в UI через `err.message === '...'`.
