## Пивот: Blaze заблокирован → polling через GitHub Actions

После публикации хэндоффа ниже пользователь попытался включить Blaze и упёрся в блокировку на стороне Google: карта прошла верификацию (деньги за холд вернулись автоматически через пару минут — с оплатой всё в порядке), но и первый billing account, и специально созданный второй закрылись почти сразу с вердиктом **"You can't reopen this billing account because this account is not in good standing"**. Кнопка Reopen неактивна у обоих — это финальное решение антифрод-системы Google, не техническая ошибка и не что-то, что чинится повторным созданием третьего аккаунта (два из двух закрылись одинаково быстро — проблема не в конкретном аккаунте/карте). Пользователь решил не ждать ответ поддержки Google, а реализовать push без Cloud Functions.

**Решение:** тот же набор из 6 сценариев ТЗ 10, но вместо мгновенного триггера Firestore (`onDocumentCreated`/`onDocumentUpdated`, требует Blaze) — периодический опрос из GitHub Actions раз в 10 минут. Admin SDK (сервисный аккаунт) для чтения/записи Firestore и отправки FCM **не требует Blaze вообще** — это ограничение только у Cloud Functions как продукта, а не у Firestore/Messaging API как таковых.

**Что сделано:**
- `notify/index.mjs` (новый пакет, ESM) — логика всех 6 сценариев перенесена из `functions/lib/*Triggers.js` практически без изменений (тексты уведомлений, получатели, условие пропуска шаблонных предложений S9 — всё то же), только вместо event-триггера — функции `pollNewRideOffers`/`pollNewRequests`/`pollNewResponses`/`pollResponseStatusChanges`/`pollNewRequestResponses`/`pollRequestResponseStatusChanges`, каждая опрашивает свою коллекцию через `where(<поле>, '>', курсор).orderBy(<поле>)`.
- Курсоры (последний обработанный момент по каждому из 6 сценариев) хранятся в `system/notifyState` — коллекция видна только Admin SDK, в `firestore.rules` её нет и не должно быть. **При первом запуске** курсоров ещё нет — скрипт выставляет их на «сейчас» и завершается без обработки, иначе первый же прогон разослал бы push по всей уже существующей базе (все текущие открытые предложения на доске и т.п.). Это ожидаемое поведение первого запуска, не баг.
- `src/lib/db.js` — в шесть функций смены статуса отклика (`confirmResponse`, `rejectResponse`, `cancelResponse`, `confirmRequestResponse`, `rejectRequestResponse`, `cancelRequestResponse`) добавлено поле `updatedAt: serverTimestamp()`. Раньше это поле не требовалось — Cloud Functions получали событие изменения от самого Firestore и не нуждались в отдельном таймстампе; polling же должен как-то отличать «статус сменился только что» от «отклик существует уже неделю», отсюда и добавка. Firestore rules трогать не пришлось — правила `responses`/`requestResponses` разрешают update целиком обоим участникам, без ограничения по конкретным полям (`hasOnly`), в отличие от `rideOffers`.
- `.github/workflows/notify.yml` — `cron: '*/10 * * * *'` + `workflow_dispatch` для ручного запуска из вкладки Actions, `concurrency: {group: notify-polling, cancel-in-progress: false}` чтобы соседние прогоны не пересекались, если предыдущий почему-то подзавис. Секрет `FIREBASE_SERVICE_ACCOUNT` (полный JSON) пишется во временный файл, `GOOGLE_APPLICATION_CREDENTIALS` указывает на него — стандартный паттерн для Admin SDK в CI, ничего специфичного для этого проекта.
- `functions/` (пакет Cloud Functions из основной части хэндоффа ниже) **не удалён и не менялся** — если Google когда-нибудь разблокирует Blaze (после ответа поддержки, которого пользователь пока не дожидается), его можно задеплоить как есть вместо `notify/`, никакого расхождения в логике уведомлений между ними нет — `notify/index.mjs` был построен как прямой перенос `functions/lib/*.js`.

**Проверено в этой сессии:**
- `npm run build` в корне проекта — чисто, размер бандла не изменился (только `src/lib/db.js` тронут, шесть строк).
- `npm install` в `notify/` — прошёл (то же ожидаемое предупреждение `EBADENGINE` про Node 20 vs 24, что и у `functions/`, не мешает).
- `node --check notify/index.mjs` — синтаксис корректен.
- Пробный запуск `node notify/index.mjs` без реальных credentials — упал ровно на `Unable to detect a Project Id` внутри первого обращения к Firestore (`loadCursors` → `system/notifyState.get()`), то есть весь код до этой точки (импорты, инициализация, структура) отработал без ошибок — дальше нужны только настоящие credentials, которых у агента нет.

**Не проверено / за пользователем:**
1. **Создать сервисный аккаунт** — Firebase Console → Project settings (шестерёнка) → **Service accounts** → **Generate new private key**. Скачается JSON-файл. Это доступно на Spark, Blaze не нужен.
2. **Добавить секрет в GitHub** — репозиторий → Settings → Secrets and variables → Actions → **New repository secret** → имя `FIREBASE_SERVICE_ACCOUNT` → вставить содержимое скачанного JSON целиком.
3. (Опционально) **Переменную `APP_URL`** там же, во вкладке **Variables** — до появления домена хостинга (S12) можно не задавать, push будут уходить без ссылки-перехода (та же деградация, что описана в основном разделе ниже про `functions/`).
4. После этого workflow должен начать выполняться сам по расписанию; для немедленной проверки — вкладка **Actions** → **Push-уведомления (polling)** → **Run workflow** (это и есть `workflow_dispatch`).
5. Реальная проверка всех 4 сценариев на устройствах (включая iPhone, ограничение ТЗ 10 не изменилось) — с задержкой до ~10 минут вместо мгновенной доставки, которая была бы у Cloud Functions.
6. Не забыть **удалить** скачанный JSON сервисного аккаунта с диска после того, как секрет добавлен в GitHub — это чувствительный файл (полный доступ к проекту через Admin SDK), `serviceAccountKey.json` уже в `.gitignore` на случай, если он окажется в корне проекта, но лучше вообще не оставлять его лежать локально дольше необходимого.

## Важно: эта сессия начата в новой папке

В отличие от S1–S9, эта сессия работала в **свежем клоне** репозитория (`git clone` в новую папку), а не в папке с предыдущими сессиями. `.env.local` в git не попадает — пользователь заново прислал ключи `firebaseConfig` и VAPID-ключ в чат, файл `.env.local` создан вручную с ними. Если следующая сессия тоже стартует в новой папке — этот шаг снова понадобится (ключи проекта `podvezyom` см. в Firebase Console, VAPID — в Cloud Messaging → Web Push certificates).

## Что сделано в S10

Решения в начале сессии (обсуждались с пользователем):
- **Cloud Functions на тарифе Blaze**, не клиентские триггеры. Пользователю показан примерный расчёт стоимости — при масштабе одного посёлка реалистичный счёт около 0 ₽/мес (FCM бесплатен всегда; Cloud Functions и Firestore на Blaze сохраняют те же бесплатные квоты, что и на Spark, платится только превышение). Пользователь согласился на Blaze.
- **Адресаты broadcast-уведомлений о новом предложении/запросе — все пользователи противоположной роли**, без фильтра по очереди (закрывает открытый вопрос из ТЗ 11 и из трекера). Решение пользователя.

### Серверная часть — `functions/` (новый пакет, Cloud Functions 2-го поколения)

- `functions/lib/messaging.js` — `sendToUser(uid, tokens, payload)` (`admin.messaging().sendEachForMulticast`, чистит невалидные токены из `users/{uid}.notificationTokens` через `arrayRemove` по кодам ошибок `registration-token-not-registered`/`invalid-argument`/`invalid-registration-token`), `sendToUid` (читает токены пользователя сама), `sendToUsers` (рассылка списку пользователей).
- `functions/lib/broadcastTriggers.js` — `onRideOfferCreated` (новое предложение → всем `isCustomer`; **пропускает** документы с полем `templateId`, иначе публикация повторяющегося шаблона S9 на месяц вперёд шлёт каждому заказчику до 30 push одним действием водителя — решение принято по ходу, не обсуждалось отдельно с пользователем, но напрямую следует из механики S9), `onRequestCreated` (новый запрос → всем `isDriver`).
- `functions/lib/responseTriggers.js` — `onResponseCreated` (новый отклик заказчика → водителю-владельцу предложения), `onResponseUpdated` (смена `status`: `confirmed`/`rejected` → заказчику-автору отклика, `cancelled` → водителю — по коду `db.js`, отмену подтверждённого отклика всегда делает заказчик, п. 7.7 ТЗ).
- `functions/lib/requestResponseTriggers.js` — зеркально предыдущему для откликов водителей на запросы (`onRequestResponseCreated`/`onRequestResponseUpdated`, роли развёрнуты: `cancelled` инициирует заказчик п. 8.4 ТЗ → уведомляется водитель).
- **`webpush.fcmOptions.link` требует абсолютный HTTPS-URL** — у проекта его пока нет, хостинг только в S12. Решение: ссылка в push добавляется, только если в `functions/.env` задан `APP_URL` (шаблон — `functions/.env.example`); без него push уходит без ссылки-перехода (клик просто открывает/фокусирует вкладку) — деградация, не ошибка отправки. **Не забыть задать `APP_URL` в S12**, когда появится домен хостинга.
- Правила Firestore **не менялись** — токены хранятся полем `notificationTokens` в `users/{uid}`, который и так пишет только владелец (правило `S1` не изменилось); Cloud Functions читают всех пользователей через Admin SDK в обход правил, им это не нужно.
- `functions/package.json` (`firebase-admin`, `firebase-functions`, `engines.node: "20"`), `functions/.gitignore`, `.firebaserc` (`{"projects":{"default":"podvezyom"}}`), `firebase.json` (только `functions.source`). Зависимости установлены (`npm install` в `functions/`), `require('./functions/index.js')` проверен вручную — грузится и экспортирует все шесть функций без ошибок. **Firebase CLI (`firebase-tools`) установлен глобально** на этой машине.

### Клиентская часть

- `src/lib/notifications.js` — `enableNotifications(uid)` (запрашивает разрешение → регистрирует `/firebase-messaging-sw.js` → `getToken` → сохраняет в профиль), `disableNotifications(uid)`, `getCurrentToken()` (не спрашивает разрешение, только читает уже выданный токен — на нём строится состояние тумблера, не на `Notification.permission` напрямую: разрешение браузера липкое и код не может его сбросить программно при отключении, а вот регистрация токена в профиле — да), `listenForegroundMessages()`. Обёртка над `firebase/messaging`, `isSupported()` из самого SDK отсекает недоступные контексты (в т. ч. iPhone-вкладку вне PWA — там просто нет `Notification`).
- `src/lib/db.js` — `addNotificationToken`/`removeNotificationToken` (`arrayUnion`/`arrayRemove` на `users/{uid}.notificationTokens`, массив — не одно поле, чтобы push работал на нескольких устройствах пользователя разом).
- `src/components/NotificationsToggle.jsx` (новый) — чекбокс в профиле: статус поддержки, статус разрешения, ошибки понятным текстом (`permission-denied` → «заблокированы в настройках браузера», без деталей о токене). Подключён в `src/screens/Profile.jsx`.
- `src/App.jsx` — слушает foreground-сообщения (вкладка открыта и в фокусе — SDK не показывает их сама, только фоновые показывает сервис-воркер), показывает через `new Notification()`.
- `public/firebase-messaging-sw.js` (новый) — конфиг Firebase захардкожен внутри файла: `public/` Vite не обрабатывает, `import.meta.env` там не подставляется, а ключ веб-приложения Firebase не секрет (защита — правила Firestore/Auth, не он).
- `.env.example` уже содержал `VITE_FIREBASE_VAPID_KEY` с прошлой сессии — просто заполнен.

## Особенности окружения (не меняются с S1, плюс новое из S10)

- **Node не в PATH.** `C:\Program Files\nodejs\node.exe` (v24.18.0 на момент S10, npm 11.16.0). В PowerShell: `$env:Path = "C:\Program Files\nodejs;$env:Path"`.
- **`functions/package.json` просит Node 20** (Cloud Functions 2-го поколения не поддерживают 24) — при `npm install` в `functions/` будет предупреждение `EBADENGINE`, это ожидаемо и не мешает: локальный Node нужен только чтобы `npm install`/статически проверить require, реальный рантайм в облаке — свой, версию берёт из `engines.node`.
- **GitHub CLI не в PATH** — `& "C:\Program Files\GitHub CLI\gh.exe"`.
- **Vite слушает только `::1`** без явного host. В `vite.config.js` прописан `host: '127.0.0.1'`. Не убирать.
- Git-идентичность в этой папке взята из глобального конфига машины (`djachkova-ux` / `djachkova@kefir-media.com`) — совпадает с реальным аккаунтом пользователя, локального оверрайда не потребовалось (в отличие от заметки про `alati74` в более старой копии проекта на этой же машине — та относится к другой локальной папке, не к этой).
- **Firebase-проект:** `podvezyom`. **Тариф — Spark на момент конца S10** (переход на Blaze размечен как шаг за пользователем, см. выше). Firestore rules по-прежнему публикуются только вручную через Console → Rules → Publish, CLI-деплой rules не настроен (в S10 это не понадобилось — правила не менялись). **Firebase CLI (`firebase-tools`) установлен глобально в S10** — раньше не был нужен вообще, теперь нужен для `firebase deploy --only functions`.
- **Порт dev-сервера** — в этой сессии запускался напрямую через `node .../vite.js podvezem` (не через `npm run dev`, так как сессия работала из родительской папки `D:\Работа\Школьный трансфер`, а не из `podvezem`); добавлен `D:\Работа\Школьный трансфер\.claude\launch.json`, отдельный от `podvezem\.claude\launch.json` (тот остаётся для запуска изнутри самой папки `podvezem`, если следующая сессия будет работать оттуда).

## Принятые решения (накопительно)

- Push — через Cloud Functions на Blaze, не клиентские триггеры (см. «Что сделано» выше).
- Broadcast-уведомления (новое предложение/запрос) — всем противоположной роли, без фильтра по очереди. Закрывает открытый вопрос ТЗ 11.
- Предложения из шаблона (`templateId` есть) не триггерят broadcast-push — иначе шаблон на месяц вперёд спамит.
- Ссылка в push (`fcmOptions.link`) — опциональна через `APP_URL` в `functions/.env`, до появления домена хостинга (S12) просто не добавляется.
- Иконка в push не задана — иконок PWA ещё нет (S11), браузер покажет свою по умолчанию; можно добавить `webpush.notification.icon` в `functions/lib/messaging.js`, когда иконки появятся.
