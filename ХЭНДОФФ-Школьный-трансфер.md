## Что сделано в S7

Зеркальный сценарий S6: водитель откликается на запрос заказчика (без выбора детей — отклик на весь запрос целиком), заказчик подтверждает или отклоняет; подтверждение закрывает запрос транзакцией.

**Решён открытый вопрос из хэндоффа S6** (схема отклика водителя): выбрана **отдельная коллекция `requestResponses`**, а не переиспользование `responses` с полем-различителем направления. Причина: у запроса нет счётчика мест (`seatsFree`), поля и правила похожи на `responses`, но по смыслу — разные сущности; отдельная коллекция чище и не тащит на каждый документ поле-различитель, которое где-то не глядя забудут проверить.

- **`src/lib/db.js`** — добавлены: `subscribeRequest(requestId, callback)` (подписка на один запрос, аналог `subscribeRideOffer`); `createRequestResponse(uid, profile, request, { note })` — публикует документ в `requestResponses` со снимком данных водителя (`driverName`, `driverPhone`, `driverCar`, `pickupQueues`) и **`requestCustomerId`** (денормализованный владелец запроса — по аналогии с `offerDriverId` в S6); `subscribeRequestResponses(requestId, customerUid, callback)` — запрос по `requestId` **и** `requestCustomerId` (тот же приём из «Важного технического урока» S6 — фильтровать по полю, которое проверяет правило `read`, — применён сразу, без повторного наступления на грабли); `confirmRequestResponse(response)` — `runTransaction`: у запроса нет мест, поэтому подтверждение **любого одного** отклика сразу переводит запрос в `status: 'closed'`; транзакция проверяет `request.status === 'open'` (иначе `already-closed`) и `response.status === 'pending'` (иначе `already-handled`); `rejectRequestResponse(responseId)` — обычный `updateDoc`, без транзакции.
- **`firestore.rules`** — новый блок `requestResponses`, симметричный `responses`: `read` — участники (`driverId` или `requestCustomerId`), `create` — водитель, `update` — заказчик-владелец запроса. `delete` не разрешён никому (S8). **Опубликован пользователем в консоли, проверено.**
- **`src/screens/RequestRespondSheet.jsx`** (новый, `/board/requests/:requestId/respond`) — водитель отправляет отклик с необязательным комментарием. Без выбора детей (в отличие от `RespondSheet.jsx` из S6). Гейт по `isDriver && car.plate && pickupQueues.length > 0` (те же условия, что в `NewOffer.jsx`). Отдельное состояние «запрос больше не открыт».
- **`src/screens/RequestResponses.jsx`** (новый, `/board/requests/:requestId/responses`) — заказчик видит список откликов водителей (карточка `DriverResponseCard`, переиспользует классы `board.css`): имя, авто, очереди, телефон с `tel:`-ссылкой. Кнопки «Подтвердить»/«Отклонить» для `pending`; кнопка подтверждения дополнительно дизейблится на UI, если запрос уже закрыт. Гейт по `request.customerId === user.uid`.
- **`src/components/RequestCard.jsx`** — кнопка «Откликнуться» из `disabled`-заглушки стала `Link` на `RequestRespondSheet` (чужой запрос) или на `RequestResponses` («Отклики», свой запрос).
- Два новых маршрута в `App.jsx`.

## Проверено в браузере — сценарий целиком

Тестовыми аккаунтами `+7 900 222-33-01` (заказчик Ирина Ковалёва), `...-02` (водитель Дмитрий Панов) и `...-03` (водитель Марина Швец):
- **Подтверждение:** заказчик 01 создал запрос → водитель 02 откликнулся с комментарием «Заеду в 7:50» → заказчик 01 зашёл в «Отклики», нажал «Подтвердить» → запрос получил `status: 'closed'`, отклик — `confirmed`, запрос пропал с доски «Запросы» (было 1, стало 0).
- **Отклонение:** заказчик 01 создал второй запрос → водитель 03 откликнулся → заказчик 01 нажал «Отклонить» → отклик получил `status: 'rejected'`, запрос остался `status: 'open'` и виден на доске.
- Гейты (`RequestRespondSheet` для незаполненного профиля водителя, `RequestResponses` для чужого запроса) — не проверялись отдельно в этой сессии (код идентичен по структуре уже проверенным гейтам S6/S5), но подтверждены косвенно: маршрутизация и права `isOwn`/чужой отрабатывали верно на всех шагах сценария.
- Гонка двух подтверждений разных откликов на один запрос — не воспроизводилась намеренно (как и `not-enough-seats` в S6), но механизм в `confirmRequestResponse` заложен по коду: вторая транзакция при повторном чтении увидит `request.status !== 'open'` и бросит `already-closed`.
- `npm run build` — чисто, только ожидаемое предупреждение про размер чанка (~828 кБ / 245 кБ gzip).

Полный обход двух устройств не делался — тестировалось последовательным переключением аккаунтов в одном браузере, стандартный способ проверки в этом проекте.

## Принятые решения (накопительно)

- Схема `responses` (S6): `offerId`, `offerDriverId`, `customerId`, `customerName`, `customerPhone`, `address`, `homeQueue`, `children[]` (снимок `{id, name, age}`), `date`, `arrivalTime`, `note?`, `status: 'pending' | 'confirmed' | 'rejected'`, `createdAt`.
- **Схема `requestResponses` (S7):** `requestId`, `requestCustomerId` (денормализация ради правил и list-запроса без composite-индекса — симметрично `offerDriverId`), `driverId`, `driverName`, `driverPhone`, `driverCar` (снимок `{plate, brand, color}`), `pickupQueues[]`, `date`, `arrivalTime`, `note?`, `status: 'pending' | 'confirmed' | 'rejected'`, `createdAt`. **Нет `seatsFree`/`children[]`** — в отличие от `responses`, водитель откликается на запрос целиком, не выбирая часть.
- **List-запросы и security rules: фильтровать по тому полю, что проверяет правило `read`** — правило закреплено в S6, применено в S7 сразу для `subscribeRequestResponses` (фильтр по `requestCustomerId`), сработало без ручного создания индекса, как и ожидалось.
- Уменьшение `seatsFree` (`responses`) и смена `status` запроса (`requestResponses`) — только внутри одной `runTransaction`, которая заново читает оба документа. Общий паттерн для обеих коллекций, проверен в обоих направлениях (S6 — предложения, S7 — запросы).
- `delete` не разрешён ни для `responses`, ни для `requestResponses` — отмена отклика/снятие подтверждённого резерва — S8.
- «Активная поездка» отдельной сущностью не заводится ни для одной из сторон — подтверждённый отклик (`responses.status === 'confirmed'` или `requestResponses.status === 'confirmed'`) уже содержит нужные данные; экран «Мои поездки» (S8) будет читать обе коллекции и объединять на клиенте.
